# ski-demo — login (BCP admin)

**Purpose: VIDEO SEED** — raw footage for a help/promotional video, to be finished in the
Video-Editor repo. Not a bug repro.

**What this clip is FOR.** This is the shared sign-in opening — email, the four-digit code,
the dashboard — recorded ON ITS OWN so an editor can drop it over the front of `add-item`,
`add-question`, `add-requirement` and `add-collection`. All four of those open with the same
sign-in; improving that opening once here means it never has to be re-recorded inside all four
full takes again. **It is cut to end exactly where each of those four videos' own third screen
begins** — settled on the Dashboard, no logout — so it is a drop-in replacement for their
opening, not a new video with independent restrictions.

- **Recorded:** 2026-09-09, localhost (mandatory for video seeds — ski-demo also exists in
  production, but production was never touched)
- **Target:** dev (`http://localhost:8080`), store `ski-demo`, business `Rentify Demos Corp`
- **Surface:** BCP admin (`bcp_runner.ts`), sequence `login` (`login_only` flow — sign in, verify,
  settle on the dashboard; no logout)
- **Command:**
  ```
  CLICK_HIGHLIGHT_FILL=0 TYPE_HIGHLIGHT=1 \
  SCREEN_MIN_MS="6200,6500,2500" \
  RECIPE=login npx tsx scripts/record_flow.ts --surface bcp ski-demo login
  ```

## The four PIN-box checks — the whole point of this clip

Each box is now clicked and ringed FIRST, then given its one digit, so the yellow highlight ring
steps across the row instead of parking on box 1 while digits land elsewhere. Frame-verified
directly against the delivered mp4 (`ffmpeg -ss <t> -frames:v 1`):

| digit | timestamp | state confirmed |
|---|---|---|
| box 1 | **t = 7.10s** | box 1 has the yellow ring, cursor visible, boxes 2-4 empty |
| box 2 | **t = 8.00s** | box 1 = "1", box 2 has the yellow ring, boxes 3-4 empty |
| box 3 | **t = 9.00s** | boxes 1-2 = "1", box 3 has the yellow ring, box 4 empty |
| box 4 | **t = 12.10s** | boxes 1-3 = "1", box 4 has the yellow ring — confirmed BEFORE the auto-submit |

**The ring steps correctly on all four boxes, including box 4.** This is the one that matters
most: the code field is a Mantine PIN input that auto-submits the instant the 4th digit lands, so
if the ring were not already on box 4 before that digit was typed, it would never be seen there
at all. It was — the digit for box 4 doesn't land until ~12.80s (dashboard visible by ~12.84s),
well after the ring is already in place at 12.10s.

One timing note for whoever reads the raw log afterward: there is a ~2.3s gap between box 3's
digit landing (~9.64s) and box 4's ring appearing (~12.00s) that is NOT dead time — it is
`SCREEN_MIN_MS`'s second value (6500ms) being held out on the code screen *before* the box-4
click, because typing box 4 ends the screen via auto-submit and there is no "after" left to hold
against. The console log's own accounting (`screen 2 the code screen: on for 4.3s, holding 2.2s
more to reach 6.5s`) matches this.
